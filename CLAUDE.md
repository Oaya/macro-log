# MacroLog - Fitness & Nutrition Tracker

A GraphQL API for tracking food, workouts, body metrics, and personalized nutrition goals. Monorepo: `backend/` (API, complete) and `mobile/` (React Native, planned).

## Tech Stack

- **Python 3.12** + **FastAPI**
- **Strawberry** (code-first GraphQL)
- **SQLAlchemy 2.0** (`Mapped` / `mapped_column`, `DeclarativeBase`)
- **Alembic** (migrations)
- **PostgreSQL 16**
- **Docker** + Docker Compose (local dev)
- **JWT** (PyJWT) auth + **bcrypt** hashing
- Deployed on **Render**

## Project Structure

- `backend/main.py` - FastAPI app + GraphQL context (auth) wiring
- `backend/database.py` - engine, SessionLocal, Base
- `backend/models.py` - SQLAlchemy models
- `backend/security.py` - hash/verify passwords, create/decode JWT
- `backend/calculations.py` - pure nutrition math (BMR, TDEE, macros, age) - NO db/GraphQL
- `backend/openfoodfacts.py` - external food-search API (Search-a-licious)
- `backend/seed.py` - seeds exercises (idempotent)
- `backend/gql/` - GraphQL layer; partial Query/Mutation classes merged in `schema.py`
  - `types.py`, `inputs.py`, `converters.py`
  - `auth.py`, `food.py`, `user.py`, `workout.py`, `goal.py`, `summary.py`
- `backend/alembic/versions/` - migrations

## Running Locally

```bash
docker compose up --build -d       # start backend + db
docker compose logs -f backend     # tail logs
```

GraphQL playground: http://localhost:8000/graphql
Hot reload is on (uvicorn `--reload`), so code edits apply without rebuild. Rebuild only when `requirements.txt` changes.

## Migrations (run inside the container)

```bash
docker compose run --rm backend alembic revision --autogenerate -m "message"
docker compose run --rm backend alembic upgrade head
```

**ALWAYS read autogenerated migrations before applying.** Known gotchas:

- Alembic does NOT auto-create Postgres enum types on `add_column`. Manually add `sa.Enum(...).create(op.get_bind())` before the `add_column`, and drop it in `downgrade`.
- Adding a NOT NULL column needs a `server_default` (or the migration fails on existing rows).
- Never edit an already-applied migration - it desyncs files from the DB.

## Seeding

```bash
docker compose run --rm backend python seed.py   # idempotent, safe to re-run
```

## Conventions

- **SQLAlchemy 2.0 style only**: `Mapped[type] = mapped_column(...)`. No legacy `Column(...)`.
- **Units are stored canonically**: weight in **kg**, height in **cm**. Convert at the API boundary using the user's `unit_preference` (METRIC/IMPERIAL). Never store mixed units.
- **Dates**: user-facing logs use `log_date` (a `Date` - which day the entry is _for_), distinct from `created_at` (timestamp - when the row was created).
- **GraphQL enum → DB string**: assign `.value` (e.g. `meal_type.value`). DB string → GraphQL enum: wrap it (e.g. `MealType(db_value)`).
- **Two "User" objects**: `UserModel` (SQLAlchemy, has `password_hash`) vs GraphQL `User` (no `password_hash`). Resolvers work with `UserModel` internally, return GraphQL types via converters. Never expose `password_hash`.
- **DB access**: `select(...).where(...)` then `.scalars().all()` or `.scalar_one_or_none()`. Always wrap sessions in `try/finally: db.close()`.
- **Formatting**: Ruff, 4-space indent, format on save. `# noqa: F401` on intentional side-effect imports (e.g. models in `env.py`).

## Auth

- **Public** (no token): `register`, `login`, `searchFoods`, `exercises`
- **Protected** (require token): `me`, `logFood`, `foodLogs`, `updateProfile`, `recordWeight`, `bodyWeights`, `logWorkout`, `workoutLogs`, `setWeightGoal`, `goal`, `dailySummary`
- Protected resolvers get the user via `info.context["current_user"]` and raise `"Not authenticated"` if it's `None`.
- Clients send `Authorization: Bearer <token>`.

## Domain Logic

- **Food logging**: `searchFoods` hits an external API (returns unsaved results); `logFood` snapshots the food into the DB so historical nutrition never changes.
- **Custom foods**: `Food.created_by_user_id` (nullable) + `is_public` support user-created private foods (model ready).
- **Body weight**: one entry per user per day (unique constraint on `user_id, recorded_date`); `recordWeight` upserts.
- **Exercise calories**: `MET × latest body weight × (duration_min / 60)`. Null if no duration or no recorded weight (honest - strength-only logs get no estimate).
- **Goal calculation**: Mifflin-St Jeor BMR → activity-adjusted TDEE → subtract deficit for the weight target (7700 cal/kg) → split into macros (30/40/30, at 4/4/9 cal/g). Floored at a safe minimum. Inputs (`target_weight_kg`, `target_date`, `activity_level`) stored on `Goal` so it's reproducible.
- **Daily summary**: aggregates food (calories in + macros), workouts (calories out), and the goal (targets) for a given date.

## Testing

- **Framework**: pytest (with `pytest-asyncio` if testing async resolvers).
- **Test database**: integration tests MUST use a separate test database, never the dev DB. Create/drop tables per test session; roll back or truncate between tests so they're isolated.
- **Structure**: mirror the source layout — `tests/test_calculations.py`, `tests/test_auth.py`, `tests/test_food.py`, `tests/test_user.py`, `tests/test_workout.py`, `tests/test_goal.py`, `tests/test_summary.py`.

### Coverage expectations

- **Pure functions** (`calculations.py`) — unit tests, no DB. Cover normal cases, boundaries, and edge cases (e.g. BMR for both sexes, macro split sums back to calories, safety floor triggers, age calculation around birthdays).
- **Every GraphQL query and mutation** — an integration test per resolver, covering:
  - **Happy path**: valid input returns expected result.
  - **Auth**: protected resolvers reject requests without a valid token ("Not authenticated"); public ones work without one.
  - **Validation/errors**: bad input is rejected (duplicate email on register, wrong password on login, incomplete profile on setWeightGoal, etc.).
  - **Ownership**: a user only sees/affects their own data (can't read another user's logs).
- **Key domain logic** — e.g. logFood snapshots food correctly, recordWeight upserts (one per day), exercise calories compute from MET × weight × duration (and are null without duration/weight), dailySummary aggregates food + workouts + goal correctly.

### Per-resolver test checklist

For each query/mutation, test at minimum:

1. Works with valid input + valid auth.
2. Rejects when auth is required but missing/invalid.
3. Rejects/handles invalid input.
4. Returns only the current user's data (where applicable).

## Deployment (Render)

- Web service builds from `backend/Dockerfile`, runs `start.sh` (migrations + seed + uvicorn on `$PORT`).
- `database.py` rewrites Render's `postgres://` URL to `postgresql://`.
- Free Postgres expires 30 days after creation; recreate + redeploy restores schema/seed automatically (user data is lost).
